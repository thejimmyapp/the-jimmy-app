## Verified facts

### 1. `move=23b`: parsing and application

`view.html` constructs `URLSearchParams` from the query string and reads the first `move` value with `searchParams.get("move")` ([`view.html:29-35`](https://github.com/bmacho/bughouse-viewer/blob/adfa1820859369d3376b8c41128b0ae82e9099b3/view.html#L29-L35)). After loading the generated BPGN, it first advances to the end, then conditionally calls `asstomove` if the parameter is non-empty ([`view.html:190-195`](https://github.com/bmacho/bughouse-viewer/blob/adfa1820859369d3376b8c41128b0ae82e9099b3/view.html#L190-L195)):

```js
v1.reloadgame(bpgn1, "", "")
assforward(999,'c','v1',0)

if (move_param) {
    asstomove(move_param,v1)
}
```

`searchformove` applies the unanchored regular expression `/(\d+)([aAbB])/`, parses the digit run with `parseInt`, preserves the letter's case, then follows only `nNext[0]`, the main line, until both `nMove` and `cBoard` match ([`hy.js:3944-3977`](https://github.com/bmacho/bughouse-viewer/blob/adfa1820859369d3376b8c41128b0ae82e9099b3/hy.js/hy.js#L3944-L3977)):

```js
let match = movestr.match(/(\d+)([aAbB])/);
let targetMoveNum = parseInt(match[1]);
let targetBoard = match[2];
// ...
if (d?.nMove == targetMoveNum && d?.cBoard == targetBoard) return ind
else if (d?.nNext) ind = d.nNext[0]
```

The four case-sensitive board/side tokens are declared as `A`, `a`, `B`, and `b` ([`hy.js:173-177`](https://github.com/bmacho/bughouse-viewer/blob/adfa1820859369d3376b8c41128b0ae82e9099b3/hy.js/hy.js#L173-L177)). Therefore the intended address grammar is:

```text
{moveNumber}{A|a|B|b}
```

- `A`: White's numbered move on board A.
- `a`: Black's numbered move on board A.
- `B`: White's numbered move on board B.
- `b`: Black's numbered move on board B.

Thus `23b` means **Black's 23rd move on board B**.

When a match is found, `asstomove` rewinds to the root and calls `forwardmove` for every array index from `1` through the matched index, inclusive ([`hy.js:3979-4021`](https://github.com/bmacho/bughouse-viewer/blob/adfa1820859369d3376b8c41128b0ae82e9099b3/hy.js/hy.js#L3979-L4021)). The displayed state is therefore **after `23b` has been played**, not immediately before it.

Verified edge cases:

- The comments say dotted forms such as `14.a` work, but the implementation contradicts the comments: the digit and board letter must be adjacent. `23.b` does not match.
- The regex is not anchored. `x23b-anything` matches the `23b` substring, and `23B Nf2` matches `23B`.
- It accepts any number of digits and leading zeroes; `00023b` becomes move number `23`. `0b` is syntactically accepted but will normally find no move-zero node.
- Letter case is semantic and is not normalized.
- Only the main line is searched. Variations under `nNext[1...]` are ignored.
- Empty `move=` is falsy and is not applied. Invalid or absent addresses are silent.
- If the address is invalid or not found, `asstomove` does nothing. Because `view.html` advanced to the end first, the viewer remains at the end of the game.
- `URLSearchParams.get` uses the first duplicate query value and percent-decodes it; a URL fragment is not part of the query.
- Links generated by `refreshURLBox` are narrower than links accepted by the search parser: they extract only an anchored one-to-four-digit address with `/^\d{1,4}[aAbB]/` ([`hy.js:4032-4048`](https://github.com/bmacho/bughouse-viewer/blob/adfa1820859369d3376b8c41128b0ae82e9099b3/hy.js/hy.js#L4032-L4048)).

One implementation caveat: the search follows `nNext[0]`, but the replay loop advances by numeric array indices. That is consistent with the viewer's generated linear BPGN; it is not a general variation-safe addressing algorithm.

### 2. BFEN grammar emitted by `hy.js`

#### Native form

`generatebfen` emits:

```text
<rank8>/<rank7>/<rank6>/<rank5>/<rank4>/<rank3>/<rank2>/<rank1>/<pocket> <side> <castling>
```

The implementation is at [`hy.js:1196-1243`](https://github.com/bmacho/bughouse-viewer/blob/adfa1820859369d3376b8c41128b0ae82e9099b3/hy.js/hy.js#L1196-L1243).

Piece placement follows ordinary FEN placement rules:

- ranks are emitted from rank 8 to rank 1;
- files within a rank are emitted from `a` to `h`;
- consecutive empty squares are compressed to digits `1` through `8`;
- white pieces are uppercase and black pieces lowercase;
- ranks are separated by `/`.

The function appends `/` after rank 1 and then appends the pocket string. An empty pocket therefore leaves a trailing slash immediately before the space preceding side-to-move.

#### Promoted marker

An internally promoted piece is stored with an uppercase type letter by `promotion` ([`hy.js:3523-3541`](https://github.com/bmacho/bughouse-viewer/blob/adfa1820859369d3376b8c41128b0ae82e9099b3/hy.js/hy.js#L3523-L3541)). During BFEN generation, an uppercase internal type gets a `~` suffix before color casing is applied ([`hy.js:1216-1221`](https://github.com/bmacho/bughouse-viewer/blob/adfa1820859369d3376b8c41128b0ae82e9099b3/hy.js/hy.js#L1216-L1221)). Examples:

```text
Q~   promoted white queen
q~   promoted black queen
```

The marker distinguishes a promoted piece from an original piece of that type, which matters when a captured promoted piece must revert to a pawn in drop variants.

#### Pocket ordering and case

`holdText` serializes counts by repeating piece letters in this exact canonical order ([`hy.js:1535-1573`](https://github.com/bmacho/bughouse-viewer/blob/adfa1820859369d3376b8c41128b0ae82e9099b3/hy.js/hy.js#L1535-L1573)):

```text
B N R Q r q b n p P
```

That is: White bishops, knights, rooks, queens; Black rooks, queens, bishops, knights, pawns; then White pawns. Case denotes the owner of the pocket piece. Kings are never serialized. There are no separators between pieces and no numeric count syntax; two white knights are `NN`.

#### Side-to-move and remaining fields

`whosmove` emits `b` for a lowercase internal turn token and `w` otherwise ([`hy.js:575-577`](https://github.com/bmacho/bughouse-viewer/blob/adfa1820859369d3376b8c41128b0ae82e9099b3/hy.js/hy.js#L575-L577)). `generatebfen` then emits castling rights in `KQkq` order, omitting unavailable letters ([`hy.js:1232-1242`](https://github.com/bmacho/bughouse-viewer/blob/adfa1820859369d3376b8c41128b0ae82e9099b3/hy.js/hy.js#L1232-L1242)). If there are no rights, it emits an empty castling field rather than `-`.

This BFEN omits en-passant, halfmove, fullmove, and clock fields. The commented code shows board clocks were deliberately not appended.

#### Bracket form

`bfen_to_bracket_notation` converts only the first whitespace-delimited token ([`hy.js:1245-1266`](https://github.com/bmacho/bughouse-viewer/blob/adfa1820859369d3376b8c41128b0ae82e9099b3/hy.js/hy.js#L1245-L1266)):

```text
rank8/.../rank1/pocket w KQkq
            becomes
rank8/.../rank1[pocket] w KQkq
```

An empty pocket becomes `[]`. If the input contains `[` anywhere, the function returns it unchanged. It performs no structural validation; malformed extra slash segments after rank 1 are coerced through a JavaScript array and can become comma-separated inside the brackets.

### 3. Online Drophouse Stockfish handoff contract

Both viewer-board Analyze buttons construct the same target, using board A's or board B's generated BFEN respectively ([`hy.js:4897-4905`](https://github.com/bmacho/bughouse-viewer/blob/adfa1820859369d3376b8c41128b0ae82e9099b3/hy.js/hy.js#L4897-L4905), [`hy.js:4941-4948`](https://github.com/bmacho/bughouse-viewer/blob/adfa1820859369d3376b8c41128b0ae82e9099b3/hy.js/hy.js#L4941-L4948)):

```text
https://online-dropchess-stockfish.onrender.com/analysis.html?fen=<bracket-BFEN>
```

The source concatenates the BFEN without explicitly calling `encodeURIComponent`. A safe canonical link should percent-encode the query value. For the ordinary initial position, the verified URL is:

```text
https://online-dropchess-stockfish.onrender.com/analysis.html?fen=rnbqkbnr%2Fpppppppp%2F8%2F8%2F8%2F8%2FPPPPPPPP%2FRNBQKBNR%5B%5D%20w%20KQkq
```

On 2026-08-09 that request returned HTTP 200. Browser inspection verified:

```json
{
  "title": "Online Drophouse Stockfish",
  "data-variant": "crazyhouse",
  "data-fen": "rnbqkbnr/pppppppp/8/8/8/8/PPPPPPPP/RNBQKBNR[] w KQkq",
  "visibleEngineLabel": "Fairy-Stockfish 11+ in local browser"
}
```

The response's inline script is the complete query contract:

```js
var searchParams = new URLSearchParams(window.location.search)
var fen_in_url = searchParams.get('fen')
var default_fen = "Rn1qkbr1/pp2p2p/5n2/2pp1b2/P7/3PPP2/1PP1NN2/RNBQKB1R[Qbbnnppp] w KQ - 0 1"
document.body.dataset.fen = (fen_in_url) ? fen_in_url : default_fen
```

The site therefore reads the first decoded `fen` query value verbatim; this page does not validate or normalize it before assigning `data-fen`. The verified short viewer BFEN was accepted even though the site's fallback FEN also includes en-passant, halfmove, and fullmove fields.

The handoff is explicitly a **single-board Crazyhouse position** (`data-variant="crazyhouse"`). It is not a coupled two-board Bughouse analysis contract. Pocket contents represent the selected board's currently available drops; the URL carries no partner-board position, clocks, match event stream, or future transfer model.

#### Mapping to `building-blocks.html` block 5

The local reference defines block 5 as `[{highest-rated}({rating}) WON|LOST — {seat} {action}]`, with a silent two-board minimum-move filter and keyboard selection/open behavior (`building-blocks.html:176-182`). The conceptual mapping is:

| Block 5 field/behavior | Chess.com analog | Required Bughouse adaptation |

| Highest-rated player and rating | One of the two stacked player identity/rating rows | Select from all four linked-board seats, not only the two players on one row |

### 5. `/extraction` parser addition

The page now recognizes these additional local-only inputs:

```text
https://bmacho.github.io/bughouse-viewer/view.html?game_id=180565671769&move=23b
  -> viewer URL: game id 180565671769, move address 23b

23b
  -> move address: 23b
```

Application parsing deliberately accepts only the canonical whole-token grammar `[1-9]\d*[AaBb]`; it does not reproduce the viewer's accidental unanchored matches, leading-zero behavior, or misleading dotted-form comments. A viewer URL must use the audited host/path, contain an all-digit `game_id`, and, if present, a canonical move address. Existing username and Chess.com game URL behavior is unchanged. No network API is called.

## Assessments, assumptions, and recommendations

The following are judgments rather than verified upstream guarantees:

1. **Third-party availability risk: moderate to high.** The handoff worked and returned HTTP 200 on the audit date, but it is an unaffiliated Render-hosted site with no discovered public API contract, SLA, versioned URL, operator identity, or stability promise in the page. The `last-modified` header is from 2024; that is not a maintenance guarantee. A host migration, cold-start policy, route change, or removal can break every outbound link.
2. **The safest dependency shape is a plain outbound link.** Treat failure as non-fatal, label it “Open in Online Drophouse Stockfish (third party),” and keep a copyable BFEN fallback. Do not embed it as a required application surface.
3. **Attribution/license obligation for linking:** merely linking out does not copy or distribute the site's JavaScript, engine binary, CSS, or artwork, so this audit found no source-license notice that must be reproduced for a link. Clear third-party labeling and naming the destination is appropriate attribution. This is a product/legal assessment, not legal advice.
4. **Rate courtesy:** one explicit navigation per user click is ordinary link traffic. Do not prefetch, health-poll, iframe repeatedly, or batch-submit positions. Any future automation should first identify the operator and obtain an acceptable-use/rate agreement.
5. **Privacy:** a position placed in the `fen` query can be logged by the third-party host and intermediaries. For public games this may be low sensitivity, but the UI should not imply that analysis stays inside our application.
6. **Engine meaning:** the handoff can analyze the selected board as Crazyhouse. Calling the result “Bughouse evaluation” without explaining that it lacks the live partner-board state and future transfers would overstate what the URL conveys.
